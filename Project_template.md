# Спринт 8. Создание highload в realtime-среде

## Задание 1. Проектирование технологической архитектуры

### Анализ проблем текущей архитектуры
**Единая точка отказа:** Все сервисы и база данных развернуты в одной зоне доступности. Выход из строя этой зоны приводит к полной недоступности сервиса.

**Немасштабируемая БД:** Одна ВМ с PostgreSQL без репликации. Это "бутылочное горлышко" для производительности и главный риск потери данных. RPO=15 мин при такой конфигурации недостижимо.

**Отсутствие стратегии масштабирования:** Kubernetes кластер один, без возможности горизонтального масштабирования на несколько регионов/зон.

**Проблемы с балансировкой:** Партнеры могут "положить" API, так как нет механизмов ограничения скорости (rate limiting).

**Отсутствие мониторинга:** Команда узнает о проблемах от пользователей, что неприемлемо при требовании доступности 99.9%.

### Предлагаемое решение (To-Be Architecture)

#### 1.1 Стратегия, инфраструктура и размещение
**Использование дополнительных зон доступности:** Для выполнения требований RTO и RPO система обязательно должна быть развернута как минимум в трех зонах доступности. При выборе архитектуры Multi-Region vs Multi-Zone, останавливаемся на более простой и дешевой схеме - Multi-Zone (развертывание приложения в нескольких зонах доступности внутри одного макрорегиона). Это не решает задачи катастрофоустойчивости и снижения задержки для пользователей в различных регионах, но существенно дешевле, проще в развертывании/администрировании и достаточно для продукта только выходящего из стадии MVP.

**Выбор ЦОД (зон доступности):** Три независимых дата-центра в Москве (DC1 и DC2) и Новосибирске (DC3) с быстрыми сетевыми соединениями между всеми ними. Использование трех зон обеспечит:
- Гарантию кворума и отсутствие Split-Brain - системы координации (etcd, БД) имеют нечетное количество участников, при отказе одной из зон сохранится кворум и будет обеспечена целостность данных
- Высокую доступность (High Availability) - приложение и его компоненты распределены по 3 availability zone (AZ), в случае отказа сервис останется доступным
- Устойчивое распределение нагрузки - нагрузка при отказе одной AZ перераспределяется на две оставшиеся, что является управляемым сценарием
- Безопасность обновлений - зоны можно выводить из эксплуатации по очереди для планового обслуживания, сохраняя при этом избыточность на уровне двух AZ.

**Масштабирование:** Вертикальное масштабирование (увеличение мощности ВМ) имеет жесткий предел и не решает проблему отказоустойчивости. Поэтому выбираем горизонтальное масштабирование для среды контейнеризации. Для СУБД предел вертикального мастабирования не достигнут (объем БД и количество запросов невелики). Разместим основной сервер СУБД на физической платформе с количеством памяти, достаточным для загрузки в память всей БД.
- Сервисы (микросервисы в K8s) будут масштабироваться автоматически (HPA) на основе нагрузки (CPU, Memory, RPS)
- База данных будет развернута в виде отказоустойчивого кластера с репликацией по модели master-slave

**Самостоятельное развертывание** обеспечивает полный контроль над всей инфраструктурой:
- Аренда выделенных серверов в каждом ЦОД
- Установка и настройка собственного Kubernetes кластера
- Развертывание PostgreSQL кластера
- Управление сетевой инфраструктурой и балансировщиками нагрузки

**Географическое распределение:** Multi-Region архитектура является избыточной, так как нет требований к глобальному присутствию, а сложность и стоимость её внедрения несоизмеримо высоки для текущего состояния компании. Фокус должен быть на том, чтобы сделать стабильным и масштабируемым решение в рамках одного региона.

#### 1.2 Балансировка запросов
**Глобальная балансировка между зонами:** Anycast с поддержкой health checks (используем, например, инфраструктуру Selectel: ЦОД, DNS, каналы связи)
- В DNS для обращения к распеределенному сервису используется один IP-адрес
- Этот IP-адрес анонсируется из всех ЦОД
- BGP маршрутизация автоматически направляет трафик в ближайший ЦОД
- При отказе ЦОД, сервис мониторинга автоматически убирает его из маршрутов (BGP withdraw routes/BGP convergence), время переключения порядка нескольких минут

**Локальная балансировка в каждом ЦОД:**
- API Gateway (аутентификация партнёров, rate limiting per-partner и per-endpoint, применение SLA quotas, экстренное отключение, логирование)
- Балансировщик Ingress в кластере Kubernetes
- Health checks для всех сервисов

**Схема работы:**
- Пользователь → Anycast DNS → Ближайший доступный ЦОД
- ЦОД → API Gateway → Локальный балансировщик → Kubernetes сервисы
- Мониторинг → Автоматическое переключение маршрутизации BGP при сбоях

#### 1.3 Инфраструктура Kubernetes
**Использование одного растянутого Kubernetes кластера:**
- Три master nodes для отказоустойчивости разнесенные по ЦОД
- Автоматическое масштабирование подов (HPA)
- Автоматическое распределение подов по зонам, учитывая ресурсы и ограничения
- Anti-affinity правила для критичных подов, чтобы гарантировать их размещение в разных зонах

**Обоснование:**
- Простота: Команда уже работает с Kubernetes, переход на stretched cluster — изменение конфигурации инфраструктуры, а не кардинальное усложнение процесса разработки и деплоя (как в случае с Multi-Cluster)
- Достаточная отказоустойчивость: Вероятность одновременного падения всех трех AZ ничтожно мала - надежное решение для обеспечения SLA с партнерами
- Соответствие требованиям: Прямо решает проблему "приложение падает" из-за сбоя в одной зоне
- Cost-Efficient: Дешевле в развертывании и поддержке, чем несколько кластеров

#### 1.4 Архитектура базы данных
Репликация и использование реплик
- DC1 (Москва) — primary PostgreSQL
  - Развернут на физической платформе: 128GB RAM, NVMe SSD RAID - объем памяти достаточен для обработки БД в RAM
  - Принимает все операции записи
  - Может обслуживать операции чтения, но чтобы снизить нагрузку, обычно читают с реплик
  - Генерирует WAL 
- DC2 (Москва) — синхронная реплика (standby)
  - Работает в режиме hot standby
  - Может использоваться для операций чтения (SELECT)
  - Участвует в кворуме: запись считается подтверждённой только после ACK от этой реплики
- DC3 (Новосибирск) — асинхронная реплика
  - Обычно предназначена для disaster recovery и географической доступности
  - Может использоваться для нагрузочного распределения чтений (например, отчёты, аналитика, подготовка выгрузок)
  - Так как она асинхронная, данные могут немного отставать, поэтому критичные запросы на ней выполнять нельзя

Failover  
Если Primary (DC1) падает:
- Patroni автоматически переводит DC2 (синхронную реплику) в статус primary
- DC3 (асинхронная) перестраивается как standby для нового primary
- Все подключения через pgBouncer автоматически маршрутизируются на новый primary, приложения не замечают переключения

Резервное копирование:
- WAL-G архивация каждые 5 минут в объектное хранилище S3
- Ежедневные полные бэкапы в объектное хранилище
- Регулярное тестирование disaster recovery (DR) БД

Шардирование БД  
Решение: Не использовать на данном этапе.  
Обоснование: Общий объем данных составляет всего 50ГБ. Это очень небольшой объем для СУБД PostgreSQL. Проблема текущей архитектуры не в объеме данных, а в отсутствии репликации и отказоустойчивости.  
Планы на будущее: Шардирование — сложная технология, которая усложняет разработку и эксплуатацию. К ней следует прибегать только когда исчерпаны возможности вертикального масштабирования (более мощный инстанс БД) и репликации для чтения. Шардирование можно будет рассмотреть в будущем, если нагрузка на запись станет слишком высокой или существенно вырастет объем данных.

#### 1.5 Кеширование и использование CDN
Архитектура Redis Cluster: Развертываем отказоустойчивый Redis Cluster из 6 нод (3 master, 3 replica) с распределением по всем трем ЦОД. Каждый master узел имеет replica в другом ЦОД для обеспечения отказоустойчивости.

Стратегия кэширования данных:
- Продукты страхования: TTL 1 час с инвалидацией при изменении данных
- Результаты поиска и расчетов: TTL 5 минут для актуальности данных
- Сессии пользователей: TTL 24 часа с поддержкой distributed sessions
- Rate limiting счетчики: TTL 2 минуты для защиты API от перегрузок
- Геоданные и справочники: TTL 6 часов для снижения нагрузки на БД

Интеграция с приложением: Используем Spring Cache abstraction с Redis implementation для прозрачного кэширования на уровне приложения. Настройка различных TTL для разных типов данных через конфигурацию CacheManager.

Мониторинг и алертинг: Отслеживаем hit rate (>90%), memory usage (<70%), latency (P95 < 5ms) и replication lag (<100ms). Настраиваем алерты при отклонении метрик от нормы.

Использование CDN:
- Подключение Yandex Cloud CDN для всех статических ресурсов (HTML, JS, CSS, изображения)
- Точки присутствия: Москва, СПб, Ростов, Екатеринбург, Новосибирск, Хабаровск
- Динамические API-ответы кешируются частично (например, справочники, публичные продукты и тарифы, маркетинговая информация, публичные документы)  
Это обеспечивает одинаковое время загрузки страниц из разных регионов

#### 1.6 Сетевая инфраструктура
МежЦОДное соединение:
- Выделенный канал связи ("темное волокно") с высокой производительностью и низкой задержкой между ЦОД DC1 и DC2 в Москве 
- Каналы связи с использованием MPLS или SD-WAN между DC3 в Новосибирске и DC1, DC2 в Москве
- Резервный канал VPN через Интернет для отказоустойчивости между ЦОД DC1, DC2, DC3
- Мониторинг задержек и потерь пакетов

Балансировка трафика:
- Anycast DNS для между AZ
- Ingress внутри кластера K8s 
- Health checks всех компонентов
- Automatic failover при обнаружении проблем 

#### 1.7 Мониторинг и управление
Централизованный мониторинг:
- Infra monitoring: ресурсы ВМ, сеть, storage, Kubernetes, балансировщики
- App monitoring: сервисные метрики (latency, RPS, error rate, saturation), health-checks, JVM metrics
- Third-party monitoring: интеграции со страховыми компаниями (latency, availability, error rate), circuit breaker события
- Business metrics: конверсия в оформление полиса, SLA выполнения заявок, success rate оформления, % отказов по партнёрам

Инструменты:
- Prometheus (federation) + Grafana для мониторинга и визуализации 
- OpenTelemetry + Jaeger для трассировки
- EFK для централизованного логирования
- Alertmanager для алертинга
- Ранбуки и плейбуки для быстрого реагирования

Управление конфигурацией:
- Ansible для deployment и управления
- Использование паттерна Infrastructure as Code
- Регулярные учения по восстановлению системы

#### 1.8 Отказоустойчивость и восстановление
Автоматическое переключение:
- Удаление маршрута (BGP withdraw routes) при недоступности соответствующего ЦОД, перенаправление трафика на остальные ЦОД
- При потере связности между ЦОД по основным (выделенным) каналам переход на резервные (через Интернет)
- Использование кластера СУБД, переключение резервой реплики из standby в primary при отказе основной 
- Три master nodes Kubernetes для отказоустойчивости разнесенные по разным ЦОД
- Anti-affinity правила для критичных подов Kubernetes, чтобы гарантировать их размещение в разных зонах (ЦОДах)

Схема резервного копирования:
- Уровень 1 - Локальные бэкапы (2 разных носителя):  
  - NVMe SSD: Hot backups для быстрого восстановления (RTO < 15 минут)
  - HDD arrays: Cold storage для хранения 7-дневной истории бэкапов
- Уровень 2 - Облачное хранилище (1 копия в другом регионе):
  - Yandex Object Storage в другом географическом регионе (Санкт-Петербург)
  - Versioning и object lock для защиты от случайного удаления или ransomware
  - Шифрование данных на стороне клиента перед отправкой
- Уровень 3 - Offsite копия (дополнительная страховка):
  - Еженедельные полные бэкапы на tape storage или альтернальный cloud provider
  - Долгосрочное хранение (12 месяцев) для compliance и аудита
  - Географическое распределение в другом макрорегионе (например, Новосибирск)

Процедуры восстановления:
- Восстановление отдельных таблиц: <15 минут из локальных SSD
- Полное восстановление ЦОД: <45 минут из cloud storage + WAL archives
- Catastrophic failure: <4 часов из offsite копий с максимальным RPO<15 минут
- Разработка плейбуков для обеспечения восстановления в случае отказа различных компонентов системы
- Регулярные учения по восстановлению данных, компонентов и системы в целом

#### 1.9 API Gateway и защита от перегрузок
Внедрение API Gateway:
- Используется API Gateway (например, Kong) перед всеми B2B API
- Поддержка mTLS/JWT для аутентификации партнёров
- Rate limiting per-partner и per-endpoint (используя token bucket)
- SLA quotas: soft limit (429 с Retry-After), hard limit (drop)
- Возможность экстренного отключения партнёра через админ-панель
- Логирование всех вызовов для SLA-отчётности

Интеграция с внешними страховыми компаниями:
- Используются circuit breakers (Resilience4j) для каждого партнёра
- Таймауты + retries с backoff
- Bulkhead isolation: проблемы одного партнёра не влияют на других
- Кэширование тарифов и офлайн-обработка, если партнёр временно недоступен

#### 1.10 Планирование нагрузки (Capacity planning)
Перед рекламной кампанией:
- Нагрузочное тестирование (k6, JMeter)
- Тестируются сценарии B2C (поиск, оформление) и B2B (API вызовы)
- Определяются AutoScaling thresholds
- Pre-warming инфраструктуры (увеличение pod replicas, warm caches)
- Ранбуки на случай «flash traffic»
- Фича-флаги для отключения второстепенного функционала при перегрузке

### 2. Создание манифестов и запуск приложений
Создан манифест Deployment
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scaletest-deployment
  labels:
    app: scaletest
spec:
  replicas: 1
  selector:
    matchLabels:
      app: scaletest
  template:
    metadata:
      labels:
        app: scaletest
    spec:
      containers:
        - name: scaletest-container
          image: ghcr.io/yandex-practicum/scaletestapp:latest
          ports:
            - containerPort: 8080
          resources:
            limits:
              memory: "30Mi"
            requests:
              memory: "20Mi"
```
Создан манифест Service
```yaml
apiVersion: v1
kind: Service
metadata:
  name: scaletest-service
spec:
  selector:
    app: scaletest
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
  type: NodePort
```
Создан манифест HPA
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: scaletest-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: scaletest-deployment
  minReplicas: 1
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
```
Создано приложение locustfile.py
```python
from locust import HttpUser, between, task

class WebsiteUser(HttpUser):
    wait_time = between(1, 5)

    @task
    def index(self):
        self.client.get("/")
```
Запущены приложения
```bash
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f hpa.yaml
```
Проверен запуск hpa и получен URL для доступа
```bash
minikube service scaletest-service --url
kubectl get hpa
```
