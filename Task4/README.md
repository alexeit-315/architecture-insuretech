# Спринт 8. Создание highload в realtime-среде

## Задание 4. Проектирование продажи ОСАГО
В рамках запуска новой функциональности - продажи полисов ОСАГО, доработана архитектура системы, добавлен сервис osago-aggregator, отвечающий за взаимодействие со страховыми компаниями в процессе запроса и получения предложений на ОСАГО.
### 1. Краткое описание
Сервис osago-aggregator — специализированный асинхронный сервис с собственным лёгким хранением состояния (request-tracking), который получает запросы от core-app через sync-request API. Агрегатор отправляет запросы по партнёрским API параллельно в изолированных worker-пулах и по получению предложений по заявкам публикует события OfferReady в Message Queue. Сервис core-app подписывается на эти события и стримит их в веб-клиент через SSE.

### 2. БД для osago-aggregator
Для работы сервиса требуется небольшое хранилище (PostgreSQL) для:
- Отслеживания статусов заявок osago_request
- Хранения логов взаимодействия с партнерами
- Хранения очереди задач/флагов
- Хранения настроек (rate-limits counters, per-partner quotas)

### 3. API между osago-aggregator и core-app
Сервис osago-aggregator предоставляет REST API:
- ```POST /v1/requests``` — синхронный вызов, возвращает 202 Accepted + request_id. (core-app вызывает, получает request_id, сохраняет у себя)
- ```GET /v1/requests/{id}``` — возвращает current status + collected offers (для отладки)
- ```DELETE /v1/requests/{id}``` — отмена (если пользователь отменил)

Не ожидается, что core-app будет блочится до завершения всех partner calls — osago-aggregator должен работать асинхронно.

### 4. Интеграция между core-app и osago-aggregator
Для возврата в core-app полученнных по заявкам предложений osago-aggregator публикует события ```OsagoOffer``` (topic ```osago.requests.offers```) и ```OsagoRequestCompleted``` (topic ```osago.requests.completed```) в Message Queue (Kafka).

### 5. API между веб-приложением и core-app
Предложения должны появляться на экране **по мере поступления** от страховщиков. Для этого frontend должен получать поток предложений в реальном времени. Для этого используется Server-Sent Events (SSE) от core-app, он хорошо подходит для однонаправленного стрима обновлений.

### 6. Паттерны отказоустойчивости
#### 6.1 Rate Limiting
- В core-app — лимиты на создание новых заявок (ограничение количества активных заявок на пользователя)
- В osago-aggregator — не отклонение, а очередь + per-partner throttling; Если очередь переполнена, возвращать 503 Service Unavailable в core-app, который транслирует это пользователю
- В to-be архитектуре (на текущей схеме, базирующейся на as-is архитектуре не отображено) на входе (API Gateway) — глобальный rate limiting по клиенту/сессии (защита от ботов, всплесков)

#### 6.2 Circuit Breaker
- В osago-aggregator для каждого партнера после N отказов за период или при высокой задержке ответа на запросы расчета ОСАГО
- В core-app для платежного сервиса после N отказов за период разрыв соединения на 5 минут для предотвращения каскадных сбоев

#### 6.3 Retries
- В osago-aggregator выполняем retry вызовов к API страховой компании только при сетевых сбоях или 5xx-ошибках, не ретраим ```4xx``` (например, 400 Bad Request). Выполняем 2 попытки повтора с нарастающим сдвигом (2с - 4с). Добавляем джиттер (случайное смещение), чтобы при массовом сбое не устроить «шторма» запросов.
- В core-app выполняем retry только для идемпотентных операций (проверка статуса платежа, отмена), не ретраим создание платежей. Выполняем 2 попытки повтора с нарастающим сдвигом (2с - 4с). Добавляем джиттер (случайное смещение), чтобы при массовом сбое не устроить «шторма» запросов.

#### 6.4 Timeouts
- Request timeout - вызовы osago-aggregator к API страховой компании должны иметь ограничение по времени (2-5с), если API не ответил → считаем, что оно недоступно
- Overall timeout per request - согласно бизнес-требованию у нас есть 60с с момента получения заявки, если отдельные партнёры не ответили, по истечении этого времени osago-aggregator завершает процесс и публикует ```OsagoRequestCompleted```
- Request timeout - вызовы core-app для платежного сервиса должны иметь ограничение по времени:
  - Платежный gateway timeout: 15 секунд
  - Операция подтверждения платежа timeout: 30 секунд
  - Проверка статуса платежа: 10 секунд

### 7. Особенности масштабирования (многоэкземплярность)
Сервис osago-aggregator использует stateless workers + shared DB:
- Используются несколько экземпляров сервиса osago-aggregator
- Worker-инстансы забирают задачи из DB via leasing (SELECT FOR UPDATE SKIP LOCKED). Это позволяет горизонтально масштабировать обработку запросов в сторону партнеров

Масштабирование SSE — core-app может поддерживать необходимое количество (2500) конкурентных SSE (они stateless) соединений на одном инстансе. При необходимости масштабировать, необходимо:
- Правильно настроить ingress, выступающий в роли балансировщика
- Сервис core-app должен быть stateless
- Сервис core-app должен быть идемпотентным

Очередь сообщений — для масштабирования процесса обработки сообщений необходимо:
- Настроить Kafka в кластере из нескольких узлов (для HA и throughput)
- Настроить автоскейлинг (HPA) для consumer'ов по глубине очереди
