# Проблемы и риски текущей архитектуры InsureTech

## Текущие проблемы
1. **Синхронные запросы к ins-product-aggregator**
    - core-app и ins-comp-settlement зависят от стабильности внешних API
    - Задержки или ошибки у страховых компаний приводят к деградации работы сервисов

2. **Редкое обновление локальных реплик**
    - core-app обновляет данные раз в 15 минут, ins-comp-settlement — раз в сутки
    - В системе могут храниться и использоваться устаревшие тарифы и продукты

3. **Избыточная нагрузка на ins-product-aggregator**
    - aggregator при каждом запросе обращается ко всем страховым компаниям
    - Увеличение числа страховых компаний приведет к существенному росту нагрузки

4. **Сильная связанность сервисов через REST API**
    - ins-comp-settlement зависит от core-app для получения списка оформленных страховок
    - Ошибка или перегрузка core-app блокирует работу взаиморасчетов

5. **Нет механизма асинхронной интеграции**
    - Все взаимодействия между сервисами реализованы через синхронные запросы
    - Нет поддержки event-driven подхода

---

## Последствия роста нагрузки
1. **Рост количества страховых компаний (с 5 до 10)**
    - aggregator будет обращаться к удвоенному числу API → увеличение времени ответа и количества ошибок

2. **Увеличение числа клиентов**
    - core-app и ins-comp-settlement будут чаще делать запросы к aggregator → рост конкуренции за ресурсы

3. **Потенциальные узкие места**
    - ins-product-aggregator становится «бутылочным горлышком» всей архитектуры
    - core-app и ins-comp-settlement имеют жесткую зависимость от его SLA

4. **Сложность масштабирования**
    - Сервисы используют pull-модель (запросы к aggregator), а не push (подписка на события)
    - Масштабирование под нагрузкой приведет к росту числа параллельных REST-запросов

5. **Нет гарантии доставки и консистентности данных**
    - При сбоях в aggregator или сетевых ошибках данные о тарифах могут не обновляться
    - ins-comp-settlement может формировать отчеты на устаревших данных
---

## Риски при росте нагрузки
1. Технические риски
- Риск каскадного отказа при сбоях внешних страховых API - ins-product-aggregator синхронно ждёт ответов - один тормозящий партнёр → очередь блокируется
- Перегрузка ins-product-aggregator - из-за удвоения числа страховых компаний, количество внешних запросов увеличится вдвое, но при возникновении ошибки в запросе к одному из внешних API, core-app и ins-comp-settlement перезапрашивают данные всех внешних источников, что ведет к экспоненциальному росту числа запросов
- сore-app как bottleneck - рост количества клиентов → высокая нагрузка на сервис-оркестратор core-app (single pod) → отказ системы
- Перегрузка базы данных (PostgreSQL) - рост количества клиентов → рост числа запросов (PostgreSQL не имеет реплик, нет кеша) → рост времени отклика при чтении/записи, риск блокировок транзакций, деградация производительности
- Деградация всей системы - входной трафик поступает напрямую на сервисы (нет rate-limit, нет circuit-breaker) - «шумный» партнёр перегружает сервис-оркестратор core-app → падение производительности системы для всех партнеров и клиентов

2. Бизнес-риски
- Падение SLA (99.9%) - рост недоступности сервиса → невыполнение обязательств перед партнёрами
- Снижение NPS (лояльность клиентов) - пользователи видят «тормоза» или ошибки → ухудшается удержание
- Невозможность заключать сделки - задержки в расчёте страховки или ошибочные оформления → прямые финансовые потери
- Срыв партнёрских интеграций - внешние страховые компании могут временно отключать интеграцию из-за некорректного поведения API → прямые финансовые потери

3. Операционные риски
- Не учитываются SLA партнёров - нет формализованного SLA-контроля по API страховых компаний → неконтролируемый риск убытков из-за партнеров
- Ручное вмешательство в продакшн - попытки экстренного масштабирования (без планов DR) → риск аварии и дополнительного простоя

4. Риски безопасности
- DoS/DDoS, brute force, credential stuffing, API abuse - прямой доступ к сервису в отсутствие аутентификации, rate limiting или WAF → высокий риск непреднамеренного или преднамеренного нарушения безопасности
- Слабое разграничение прав в Kubernetes → компрометация одного pod = полный доступ

---

## Предлагаемое решение в части взаимодействия с внешними API партнеров
- Внедрение **event-driven архитектуры** с использованием брокера сообщений (Kafka)
- Использование **паттерна Transactional Outbox** для публикации событий о новых страховках (обеспечивается консистентность информации в БД страховок и очереди сообщений)
- ins-product-aggregator периодически обновляет данные из внешних API и публикует события об изменении тарифов и продуктов
- core-app публикует события о новых оформленных страховках
- ins-comp-settlement подписывается на события:
  - обновление тарифов и продуктов
  - новые оформленные страховки
- core-app подписывается на события:
  - обновление тарифов и продуктов
